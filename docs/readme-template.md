# HelloTime Pro · README 模板与对齐规范

> 本文是 20 个实现 README 的统一骨架与撰写规范（M4 交付物）。目的：让读者在任意实现的 README 之间切换时，**章节顺序、命名、信息密度一致**，能逐节并排对照。
>
> 规范基于参考栈 [`backends/fastapi/README.md`](../backends/fastapi/README.md) 的结构提炼。新实现照此模板；存量实现按 §4 的对齐审计逐步收敛。

---

## 1. 通用规则

- **语言**：正文中文（与项目其余文档一致）。代码 / 命令 / 路径保持原文。
- **开头两段固定**：
  1. `# HelloTime Pro · <栈名> <后端 / 前端 / 全栈>`
  2. 一句话定位 + 端口：技术选型（`语言 + 框架 + 关键库`）、在项目中的角色（参考实现 / M2 / M3）、监听端口。全栈再补一句「同一进程同时暴露 JSON 契约 + SSR/SPA UI」。
- **命令路径**：示例既可从仓库根（`./scripts/...`、`./verification/...`），也可从实现目录（`../../scripts/...`），二选一保持本文件内一致。
- **链接**：指向 `spec/`、`docs/`、本实现 `TECHNICAL_GUIDE.md` 用相对路径，便于点击跳转。
- **不重复 TECHNICAL_GUIDE**：README 是「怎么跑起来 + 特色速览」；深度代码导读、踩坑、跨库细节放 `TECHNICAL_GUIDE.md`，README 末尾给链接。

## 2. 章节骨架

### 2.1 后端 README

| # | 章节 | 内容 |
|---|---|---|
| 1 | `# 标题` + 定位段 | 见 §1 |
| 2 | `## 技术栈` | 表格：层次 → 选型（框架 / ORM-SQL / 数据库 / 鉴权 / 校验 / 语言运行时） |
| 3 | `## 目录结构` | 代码块 + 每个目录一行注释，体现分层（presentation → application → domain → infrastructure） |
| 4 | `## 安装与运行` | 推荐路径（dev-manager 注入 DB/LLM 配置）+ 直接运行；含「先 `scripts/db reset --seed` 准备库」提示；列 SQLite 切换、指定端口、自定义 `DB_URL` |
| 5 | `## 切换数据库驱动` | `DB_DRIVER=postgres\|sqlite` + `DB_URL` 示例表；**差异处理**列表：UUID / 时间戳 / 行锁 / 扩展索引各自怎么适配 |
| 6 | `## 实现特色` | 6–8 条要点：统一响应壳、refresh rotate + family、改密吊销、收藏计数事务一致、幂等约束，以及**本栈语言/框架的独有亮点** |
| 7 | `## 验证` | 双驱动契约命令 + 最新通过记录（`PG 104/104 · SQLite 104/104`） |
| 8 | `## 注意事项` *(可选)* | 运行限制（如 Vapor 仅 macOS）、与 spec 的对齐链接、本栈特有踩坑提示；末尾链 `TECHNICAL_GUIDE.md` |

### 2.2 全栈 README

后端骨架基础上：

- §1 定位段强调「**一个进程两套接口**」：`/api/v1/*` JSON 契约（Bearer）+ SSR/SPA UI（httpOnly cookie 或 header token）。
- §7 `## 验证` **同时**列契约（104）与 UI 冒烟（25）两组命令与记录。
- 末尾加 `## 注意事项`：说明全栈自带 UI+API、**无需 `hello switch` 代理**（仅纯前端 SPA 需要）。
- 令牌存储策略（cookie 还是 localStorage）必须按 [`docs/auth.md`](auth.md) §7.3 在 README 写明取舍。

### 2.3 前端 README

前端无数据库，章节调整为：

| # | 章节 | 内容 |
|---|---|---|
| 1 | `# 标题` + 定位段 | 框架 + 状态方案 + 路由库 + 端口 |
| 2 | `## 快速开始` | 起一个后端（默认 FastAPI，经 `:9080` 代理）+ 启动前端 + 访问地址 |
| 3 | `## 脚本` | `./run` / `./build` / `./test` 与常用 npm 脚本 |
| 4 | `## 目录结构` | 代码块 + 注释（components / pages / stores / api / utils） |
| 5 | `## 实现特色`（或 `## <框架> 特色落点`） | 框架习惯写法：Hooks / Composition API / Signals / Runes / 细粒度响应式 |
| 6 | `## 设计要点` | 状态管理、自动 refresh、主题持久化、并发守卫等跨栈同构逻辑的本栈表达 |
| 7 | `## 与契约对齐` | 路由清单、错误处理、与 `spec/` 的对应 |
| 8 | `## 验证` | `verify-ui-smoke.sh <name>` + 记录（25/25） |

> 前端无 `## 切换数据库驱动`；技术栈信息可并入定位段或 `## 脚本` 前的简表。

## 3. 写作要点

- **实现特色要「真」**：写本栈真正做了什么（如 axum「`IntoResponse` 让漏接错误编译不过」、drogon「显式 `awaitCommit` 修复异步析构提交竞态」），不写放之四海皆准的套话。
- **验证记录要新**：每次复验后更新 README 与 [`CLAUDE.md`](../CLAUDE.md) 的记录日期与比分，二者保持一致。
- **跨库差异必写**：UUID、时间戳格式、行锁三处是所有后端的公共难点，差异处理是 README 的高价值内容（详见 [`docs/db-schema.md`](db-schema.md) §4、[`docs/backend-comparison.md`](backend-comparison.md) §6–§7）。
- **鉴权一句带过 + 链接**：rotate / family / 改密吊销三条写进实现特色即可，完整语义链 [`docs/auth.md`](auth.md)，避免每个 README 重述。

**规范认定**：
- 「参考方言」（fastapi/gin/elysia）与「新派骨架」（其余后端 + next/rails）信息等价，均**视为合规**——二者的章节是同义重命名（快速开始↔安装与运行、数据库双驱动↔切换数据库驱动、契约验证↔验证、与spec对齐↔注意事项）。模板 §2 取并集，新实现从中择一即可。
- 前端五家自成一套稳定方言（§2.3），合规。
- 真正需要修的两处（nuxt 过薄/英文、nest 缺实现特色）已于 2026-06-14 修正。
- 全栈 spring-mvc / laravel 的章节名/顺序为可接受变体，内容已达标，不强制改动。
