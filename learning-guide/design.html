设计：契约长什么样

架构、数据模型、API 契约、鉴权与双库策略——这是二十份实现共同对齐的「事实源」。整理自 docs/02-design.md / auth.md / db-schema.md。

1设计原则

① 规范即单一事实源

业务契约在 spec/（OpenAPI、Design Tokens、数据字典）。所有实现必须从 spec 生成或对齐，不允许各实现自己定义。

② 栈内正交

每个实现使用该技术栈的地道写法（Signals 对 Angular、组合式对 Vue、Runes 对 Svelte），不强行统一代码结构。

③ 外部一致

不管内部怎么写，对外行为（路由、JSON 形状、错误码、样式）必须一致，肉眼可比。

④ 最小脚手架

每个实现的 run / build / test 三脚本就是用户入口，不搞复杂 CI DSL。

⑤ 教学可读优先于性能极致

不做不必要的缓存 / 优化层，代码要让读者能在 30 分钟内看完主流程。

2数据模型

四张表，关系全部 ON DELETE CASCADE。核心是 users → capsules → favorites 的多对多，外加 refresh_tokens 支撑鉴权。注意 favorite_count 是冗余计数器——为了让广场「最热」排序不必每次 JOIN+COUNT。

四张表 · 全部 CASCADE 删除 · favorites 复合主键 (user_id, capsule_id) 天然去重

3表细则与关键不变式

关键字段约束

  • email VARCHAR(254)，小写存储、大小写不敏感唯一
  • nickname VARCHAR(20)，2–20 字符、大小写敏感唯一
  • code CHAR(8)，^[A-Z0-9]{8}$，唯一
  • title 1–60、content 1–5000 字符
  • open_at > created_at + 60 秒

五个广场 / 列表索引

  • (in_plaza, favorite_count↓, created_at↓) — 最热
  • (in_plaza, created_at↓) — 最新
  • (in_plaza, open_at) — 已开/未开过滤
  • (owner_id, created_at↓) — 我创建的
  • GIN pg_trgm 模糊搜索（SQLite 跳过，全表 LIKE）

四条不变式（Invariants）

编号不变式怎么保证
I1不能收藏自己的胶囊业务层显式校验（DB CHECK 需 subquery，SQLite 不支持）
I2favorite_count == COUNT(favorites)所有 favorites 写操作必须与计数更新在同一事务内完成
I3code 严格 8 位且唯一应用层生成 + 唯一索引；撞码重试最多 5 次
I4open_at > created_at + 60s创建时校验 + DB CHECK 约束
不可变性：胶囊的 content 与 open_at 创建后永不可改（无任何更新接口）。用户可随时删除自己的胶囊，但不能编辑内容或解锁时间——「一经封存」是核心业务语义。

5鉴权设计：两种令牌

JWT(HS256) + refresh token 轮转 + 家族追踪。设计目标：无状态校验、可吊销可登出、被盗用可检测、改密后旧会话失效。

access token

  • JWT，HS256，密钥 JWT_SECRET
  • 有效期 1 小时
  • payload: sub / nickname / avatarId / iat / exp
  • 无状态：只验签查过期，不落库
  • 随请求带 Authorization: Bearer …

refresh token

  • 不透明随机串：256-bit base64url
  • 有效期 7 天
  • 落库只存 sha256，明文从不入库
  • 每条带 family_id，轮转时延续
为什么 access 用 JWT、refresh 用不透明串？access token 高频校验，无状态 JWT 避免每请求查库；refresh token 低频、必须可吊销，所以落库支持 rotate / 整族撤销。密码用 bcrypt（cost ≥ 10）存储，明文从不落库。

6Refresh 轮转 + 重放检测（核心）

每次 refresh 都是「作废旧的、签发新的、家族不变」，形成轮转链 RT₁ → RT₂ → RT₃。一旦某个已撤销的 token 被重放，说明可能被盗——立即把整个 family 作废。

refresh_tokens 表保留 family_id + revoked_at 两列，正是为了这套轮转链与整族撤销

并发坑（跨栈 review 反复出现）

轮转的「查 → 校验 → 吊销旧 → 插新」四步必须串行一致，否则两个并发 refresh 可能各自签发新 token、使链分叉。各栈处理：

策略代表实现
SELECT … FOR UPDATE 行锁（Postgres）FastAPI、Spring Boot、多数 ORM 栈
UPDATE … WHERE revoked_at IS NULL RETURNING 原子吊销推荐的无锁写法
连接池上限 1 / actor 串行化（SQLite）Axum（池=1）、Vapor（actor）
教学简化「非事务 + TODO 注释」部分实现（NestJS 等，代码顶部注明生产化做法）
改密后：吊销该用户全部未撤销 refresh token，强制其他设备重新登录。登出：幂等——无 token 或查无也返回 204；access token 不做服务端黑名单，靠 1 小时 TTL 把窗口压到可接受。

7双库策略：PostgreSQL ↔ SQLite

每个后端 / 全栈必须同时支持两库，通过 DB_DRIVER=postgres|sqlite 切换。两者在 UUID、时间戳、布尔上语义不同，这是跨栈最集中的难题：

概念PostgreSQLSQLite
UUID原生 UUIDTEXT（32 位无横线 hex，实现需一致）
时间戳TIMESTAMPTZTEXT（ISO-8601 字符串）
UUID 生成gen_random_uuid()应用层生成传入
布尔原生 BOOLEAN0 / 1
模糊搜索pg_trgm GIN 索引无扩展，全表 LIKE 扫描
行锁SELECT … FOR UPDATE无，靠串行化写入 / 池=1 / actor
字符串比较的隐患：SQLite 把时间戳存成 ISO TEXT，意味着 open_at <= now 与 ORDER BY created_at 实际是字符串比较——只有当所有写入方都用同一种 ISO 格式（带 T、统一时区偏移）时才正确。这正是 Spring Boot 双驱动回归的根因：seed 写 +00:00，而 sqlite-jdbc 期望 yyyy-MM-dd HH:mm:ss.SSS，解析失败。各栈三种解法 →

8设计令牌与赛博主题

样式体系分三层（均在 spec/styles/）：palette.css（原始色阶 50–900）→ tokens.css（语义令牌 + dark 覆盖）→ cyber.css（cy-* 共享组件类）。组件层禁止硬编码色值，一律用语义令牌或 cy-* 类，由 verify-design-tokens.sh 把关。

10开发工具与三层验证

scripts/hello · dev-manager v2

单文件 Python，零 npm 依赖。统一管理所有实现的启停 / 状态 / 日志，并合并端口代理切换。

hello start <name>   # 启动实现
hello switch <backend> # :9080 指向某后端
hello status / logs / doctor
./scripts/db init / reset --seed

三层测试策略

  • 单元：各实现内部逻辑（栈原生工具）
  • 契约：verify-contract.sh 黑盒验证 104 个 API 用例 × 双驱动
  • UI 冒烟：verify-ui-smoke.sh Playwright 25 个用例跑主流程
  • 令牌：verify-design-tokens.sh 静态比对未声明 token
验证哲学：外部黑盒脚本验证，不信任实现自报，不加实现感知捷径。这保证了「内部实现细节不重要，只要契约被满足」——也正是 20 栈能放在一起比的前提。
