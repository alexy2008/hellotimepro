对比怎么读

每个阵营都问一个最根本的问题，其余差异都从那个问题派生：

后端

同一道题，十种母语怎么解？差异落在语言表达力 × 数据访问抽象层厚度。

前端

状态变了，DOM 怎么跟着变？差异落在响应式模型——组件跑几次、依赖怎么追踪。

全栈

前后端边界画在哪？HTML 在哪一侧生成、浏览器拿到多少 JavaScript。

它们实现同一个产品、共享同一份 spec/：同一份 18 端点 API 契约、同一组 104 黑盒契约用例、同一个双库约束。全部 10 个后端均通过 verify-contract（PG + SQLite）104/104。十者之间所有差异都是纯粹的语言 / 框架 / 抽象选择差异。

数据访问：从原生 SQL 到重型 ORM 的谱系

这是后端最核心的分野。越靠原生 SQL 端，跨库越直白、行数越高、类型安全靠自觉；越靠 ORM 端，CRUD 越省、跨库适配越要钻进框架底层 SPI。

query builder

重型 ORM
FastAPI · NestJS · ASP.NET · Spring

SQL 是字符串、列名手动别名成驼峰，跨库靠自建值编解码层收敛 ←→ 表映射成强类型对象、列名拼错编译期报错 ←→ CRUD 省代码、对象模型自然，Spring Data 甚至「方法名即查询」。

同一道难题：PG / SQLite 双库适配的三类解法

A 类 · 5 家

在类型层挂适配器

ORM 不知道怎么把 uuid/时间戳存进 SQLite TEXT，于是在类型/列定义层插转换器：

  • FastAPI — SQLAlchemy Uuid + UTCDateTime
  • NestJS — ValueTransformer
  • ASP.NET — EF Core ValueConverter
  • Ktor — Exposed 自定义 ColumnType
  • Spring — @JdbcType + 自实现 ValueBinder
B 类 · 2 家

驱动分流 + 行锁分支

同时挂两个驱动，时间/UUID 走默认序列化，行锁仅 PG：

  • Gin — GORM 双驱动；clause.Locking 仅 PG
  • Ktor — Exposed 列按方言分流；forUpdate() 仅非 SQLite

（Ktor 同属 A 与 B：列类型是 A 做法，查询是 B 风格 DSL。）

C 类 · 4 家

一份 SQL + 自建值编解码

业务 SQL 只写一份（? 占位，PG 转 $n），差异收敛在「绑定」「读取」两点：

  • Vapor — uuidValue/dateValue 助手
  • Axum — Value / Cell 双枚举
  • Drogon — 全 std::string 文本协议
  • Elysia — pgSql() 把 ?→$n
抽象层最厚 → 跨库要钻得最深。Spring 的 JPA 平时最省心，但要拗它跨库时必须一路下沉到 Hibernate 的 JdbcType / ValueBinder（连 null 都要按方言给正确的 setNull 类型）——抽象帮你挡住的复杂度，在边界处原样还回来。
时间戳两策略：真正逐字符对齐 seed（+00:00 而非 Z、可变小数）的只有 6 家（Spring + 新 5 家），各有专门 WRITE formatter；其余 4 家（FastAPI/Gin/NestJS/Elysia）交给 ORM/驱动默认。手写编解码的 6 家被迫直面格式、把「字符串比较即时间比较」钉死；交给 ORM 的 4 家省了事，却把格式一致性让渡给了框架默认。

事务一致性：refresh 轮转的四个流派

旧 token 被重放时必须「先提交家族吊销、再返回 401」（事务内抛错会把吊销一起回滚）。同一要求，四种结构：

流派后端机制
① 声明式Spring@Transactional(noRollbackFor = ApiException)，直接 throw 靠注解保证吊销不被回滚
② 提交后再抛FastAPI先 commit() 提交吊销，再 raise（Python 异常不回滚已提交事务）
③ outcome 模式Gin · Ktor · ASP.NET · Vapor · Axum · Drogon事务内不抛业务错、返回 Outcome 枚举，提交后在事务外转 401（模拟 Spring 的 noRollbackFor）
④ 无事务NestJSfindOne → 改 → save，既无事务也无行锁（注释自陈教学简化）

favorite_count 计数也分两风格：原子 SQL favorite_count + 1（Gin/Ktor/Vapor/Axum/Drogon/Spring）vs EF 变更跟踪读-改-写（ASP.NET，靠 FOR UPDATE 行锁）。PG 路径普遍用 SELECT … FOR UPDATE 锁胶囊行，SQLite 靠单写事务。

响应式模型：最根本的分野

这是五框架最深层的差异，也是其余一切（为什么 props 不能解构、为什么读值要加 .value 或 ()）的根因。三大阵营：

虚拟 DOM
React · Vue · Angular
重渲染 → 算差异 → 打补丁
编译期
Svelte
构建时算好，运行时直接改 DOM
细粒度
Solid
组件只跑一次，点对点命中节点
同一个倒计时，三种写法。React 状态变才重渲染，要造无意义的 tick 逼组件重跑；Svelte/Solid 直接把倒计时放进响应式状态、定时改它；Vue/Angular 改一个被 computed 依赖的源。根因全在「组件函数执行几次」。

依赖追踪谱系：React 手写依赖数组、Vue 写 getter、Angular 用生命周期钩子 —— 三者「显式声明依赖」；Svelte 的 $effect 和 Solid 的 createEffect 自动追踪函数体里读到的响应式值。

状态管理：同一个 store 的五种写法

源码行数 vs 产物体积：几乎完全相反

全文最值得带走的一张图。写得少的（Angular 2794 行）跑起来最重（1787 KB），写得多的（Solid 3536 行）跑起来最轻（91 KB）——因为编译期/细粒度框架把「省运行时」转嫁成「源码多接线」，全家桶框架反之。

两条排序几乎完全相反 —— 抽象的成本不会消失，只会换地方出现

S全栈 · 五家

全栈比前端 / 后端多扛一层约束：一个进程要同时长出两张脸——给契约测试和浏览器 fetch 的 JSON API，给浏览器导航的 SSR HTML 页面。全部 5 套通过契约 104/104 + UI 冒烟 25/25。

边界谱系：从同构 JS 到服务端模板

全栈最根本的分野：同一个进程同时当前后端，HTML 在哪生成、浏览器拿到多少 JS？所有差异都挂在这条轴上。

五栈对「前后端边界画在哪」的不同主张

双入口架构 + cookie→Bearer 桥

双入口：一个进程，两套接口

五栈无一例外共享同一骨架：同进程暴露 JSON API（给契约 + fetch）和 SSR 页面（给导航），两张脸共用同一套业务 Service。无论是 POST /api/v1/capsules 还是创建页提交表单，最终都落到同一个 createCapsule()。

这是全栈相对「SPA + 独立后端」的最大结构红利——业务逻辑只有一份。

cookie → Bearer 桥

同一用户，契约测试眼里是 Bearer token，浏览器导航眼里是 httpOnly cookie。五栈用同一模式在入口处把 cookie「翻译」成 Bearer：

  • Spring — CookieTokenFilter（Servlet Filter）
  • Rails — CookieTokenBridge（Rack 中间件）
  • Laravel — AuthService 双读
  • Next — ht_session cookie + getServerViewer()
  • Nuxt — server middleware

跨库与招牌坑

全栈跨库适配招牌坑
Next / NuxtDrizzle 双 schema + 动态驱动RSC 服务端无 localStorage；SSR 期 window 未定义致 500
Laravel自定义 Cast + HasCrossDbKeyid 用标准 UUID cast 会让关系 JOIN 用错值；PDO 布尔 't'/'f'
RailsAR 自定义 Type + CrossDbTurbo「服务端跳转 vs 在途 fetch」时序竞态 → 收藏用同步 XHR
Spring MVCHibernate JdbcType + ValueBinderJPA 抽象最厚，跨库要下沉到底层 SPI
一个反直觉但正确的取舍：收藏为什么用同步 XHR。「点收藏 → 立刻导航到 /me/favorites」，若用异步请求，导航会 abort 掉未完成的收藏请求，事务来不及提交，跳过去看不到刚收藏的那条。同步 XHR 阻塞到事务提交后才返回，保证后续导航能看到刚写入的数据。

一体三面的结论

三篇对比是同一个道理的一体三面，最终都指向那条最值钱的主线：

抽象的成本只会换地方出现

后端：ORM 省掉平时的 SQL，换来跨库时下沉到底层 SPI。
前端：编译期/细粒度框架省运行时，换来源码多接线（Angular 源码最少、产物最重；Solid 反之）。
全栈：同构省掉前后端分离的接缝，换来客户端运行时的体量与水合复杂度。
没有免费的午餐，只有不同的账单。
