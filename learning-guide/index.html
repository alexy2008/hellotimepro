1这是什么

HelloTime Pro 不是一个应用，而是一组等价实现。它围绕同一个业务场景（时间胶囊 + 用户体系 + 胶囊广场），横向展示 20 种技术栈如何解同一道题。所有实现对外表现（API、UI、行为）必须一致，内部则使用各自技术栈的地道写法（Signals / 组合式 / Hooks / Runes / 协程 / actor……），让读者能在一个仓库里高密度对比差异。

核心承诺：因为契约、数据库语义、设计令牌、验证脚本全部共享，所以二十者之间的所有差异都是纯粹的语言 / 框架 / 抽象选择差异，而不是需求差异。这正是把它们并排阅读的价值。

本项目专为教学 / 对比 / 研究设计，不面向生产。它是老项目 HelloTimeByClaude 的破坏式升级：新增用户账号、胶囊广场、收藏、「我的」空间；移除管理员模块与桌面/移动端；把 SQLite 单驱动换成 PostgreSQL / SQLite 双驱动，把硬编码配色换成语义化设计令牌。

3业务场景：时间胶囊

业务载体是「时间胶囊」——用户写下一段内容，封存一个未来的开启时刻（openAt），到期前任何人都读不到正文，到期后才能开启阅读。围绕它长出三个支柱功能：

🔒 封存与开启

创建胶囊时定下标题、正文与开启时间，得到一个 8 位 [A-Z0-9] 唯一码。胶囊一经创建，内容与时间不可修改（可删除）。未到期返回 meta、隐藏正文；到期后返回完整正文。

🌐 胶囊广场

所有 inPlaza=true 的胶囊聚合成广场，支持最热（收藏数）/ 最新排序、已开 / 未开过滤、按标题或昵称模糊搜索、分页。列表永不返回正文。

⭐ 收藏与「我的」

登录用户可收藏任意广场胶囊（不能收藏自己的、不能收藏私密的）。「我的」空间分「我创建的 / 我收藏的」，可改昵称、头像、密码。

4角色与代表性旅程

匿名用户

浏览广场、排序、过滤、搜索、通过 8 位码开启胶囊、阅读已到期公开胶囊。

❌ 不能：创建胶囊、收藏、查看「我的」。触发收藏时前端引导登录。

注册用户

匿名用户的一切 + 创建胶囊 + 收藏 / 取消收藏 + 「我创建的 / 我收藏的」 + 改密码 / 昵称 / 头像。

❌ 不能：管理他人胶囊。没有管理员角色。

典型旅程：匿名浏览 → 看到喜欢的胶囊想收藏 → 触发登录提示 → 注册即登录 → 回首页创建胶囊、写内容选时间、获得 8 位码分享 → 别处用码开启，未到期看倒计时，到期读正文。

5架构总览

spec/ 是源头：任意实现要改行为，必须先动 spec、再动实现。验证脚本对着 spec 跑。10 个后端长得完全不同，但从外面看都是「同一个服务」；5 个前端通过 :9080 反向代理访问「当前选中」的后端——同一个前端，换后端看差异；5 个全栈各自闭环，不走代理。

spec 驱动所有实现，验证脚本黑盒校验；前端经 :9080 代理访问任一后端，全栈各自闭环

6仓库结构

HelloTimePro/
├── spec/              # 单一事实源（OpenAPI / tokens / schema / avatars / icons）
├── backends/          # 10 个后端实现（:29000–:29090）
├── frontends/         # 5 个前端 SPA（:7173–:7180）
├── fullstacks/        # 5 套全栈（:7177–:7182，自包含）
├── verification/      # 契约验证 + UI 冒烟脚本
├── scripts/           # hello CLI（dev-manager v2）+ db 维护脚本
├── docs/              # 设计与对比文档（本资料的素材来源）
└── ui-prototype/      # 设计原型（纯 HTML/CSS）

每个实现自带 ./run / ./build / ./test 三件套，脚本仅支持 macOS / Linux。数据库的 schema 初始化 / 重建 / seed 一律由仓库级 scripts/db 维护，实现自身不建表、不迁移、不 seed。

8规范即单一事实源

这是整个项目的第一原则，也是「二十份代码可逐文件并排阅读」的根本保证：

三份共享契约

  • spec/api/openapi.yaml — 18 个端点的完整 API 契约
  • spec/db/schema.sql — PostgreSQL 参考 schema（四张表）
  • spec/styles/{palette,tokens,cyber}.css — 色阶 / 语义令牌 / 共享组件类

五条设计原则

  • 规范即事实源：实现从 spec 对齐，不许自定义
  • 栈内正交：每栈用自己的地道写法
  • 外部一致：路由 / JSON / 错误码 / 样式肉眼可比
  • 最小脚手架：run / build / test 三脚本即入口
  • 教学可读优先于性能极致

9三条贯穿全项目的主线

三篇对比文档（前端 / 后端 / 全栈）反复印证同一组结论。读懂它们，二十栈的「脾气」就都解释得通：

主线一

业务逻辑与框架可彻底解耦

前端 api/types/utils 那 529 行纯 TS 在 React/Vue/Solid 间几乎逐字相同；全栈「业务 Service 只有一份」。框架真正决定的只是「状态层 + 视图层」。

主线二

某个核心模型是一切差异的根

前端是响应式模型（组件跑几次、依赖怎么追踪）；全栈是渲染模型（HTML 在哪生成）；后端是数据访问抽象层厚度。其余差异都从这里派生。

主线三

抽象的成本只会换地方出现

源码写得最少的 Angular 产物最重；ORM 平时最省心、跨库时要下沉到底层 SPI。没有免费的午餐，只有不同的账单。
