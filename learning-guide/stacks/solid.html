SolidJS

「响应式可以细到单个 DOM 节点」——组件函数只跑一次，无 VDOM、无 diff，点对点更新，产物最小（~91 KB），与 React 的最佳对照。

:7180评审 90 / 100 Solid 1.9TypeScriptVite 6@solidjs/router模块级 createStore
面向已会 React/Vue、第一次读 SolidJS 的读者。本实现与 react-ts 功能完全一致、api/types/utils 逐字复用，最适合当「同一产品的 SolidJS 译本」来读。整理自 frontends/solid/TECHNICAL_GUIDE.md（601 行）。两个核心直觉：组件函数只运行一次；响应式是细粒度的，状态读取在哪发生、更新就只刷新那一处 DOM。

1选型与一句话定位

React 用「重跑函数 + 虚拟 DOM diff」实现声明式 UI；SolidJS 用「函数跑一次 + 细粒度订阅」实现同样的声明式 UI。心智从「什么时候组件会重渲染」变成「这块响应式数据被谁订阅了」。

逻辑层逐字复用的实证：api / types / utils 在所有前端之间一字不差（Solid 直接复用 react-ts 的）——这正是契约驱动多栈的价值：业务逻辑与框架无关，框架只负责把状态渲染成 DOM。真正体现 Solid 特色的是 stores/、components/、pages/。

2细粒度响应式核心

createSignal · 最小响应式单元

const [count, setCount] = createSignal(0)。count 是 getter 函数，读值要调用 count()——只有「在响应式上下文里调用 getter」才会被记录为依赖。

createStore · 嵌套对象细粒度响应

返回 proxy，读属性路径就建立细粒度订阅。setCapsule("mine", {loading:true}) 只更新 mine 分片，订阅 favorites 的组件不被触动。

createEffect / onMount / onCleanup

createEffect ≈ useEffect 但依赖自动收集（没有依赖数组）；onMount ≈ useEffect(fn, [])；onCleanup ≈ 清理函数。

派生值：函数即 memo

派生通常就是普通函数 const cd = () => countdownTo(...)，读 cd() 时才算。昂贵计算才用 createMemo。

props 不要解构！function Card(props) ✓ 用 props.capsule.title 保持响应性；function Card({ capsule }) ✗ 解构读出当时快照、丢失后续更新。这是 React 老手最容易踩的坑。需要默认值用 () => props.x ?? 默认。

3createEffect 会追踪你「顺手读到」的依赖（招牌坑）

React 老手移植到 Solid 最隐蔽的坑，本项目实测踩过。createEffect 的依赖不是手写的，而是自动收集 effect 同步执行期间读取过的所有响应式数据——包括 effect 里调用的函数内部的同步读取。

createEffect(() => {
  if (auth.hydrated) void fetchPlaza();   // 看起来只依赖 auth.hydrated
});
async function fetchPlaza() {
  const data = await api.plaza({
    sort: plaza.sort, filter: plaza.filter, q: plaza.q,   // 这些读取在 await 之前，
    page: plaza.page,                                      // 仍在 effect 的同步追踪窗口内！
  });
}
结果：effect 实际依赖 {auth.hydrated, plaza.sort, filter, q, page, pageSize}。而 setSort/setFilter 本身已会调一次 fetchPlaza()，于是每次筛选/翻页都请求两次（序列号守卫会丢弃过期那次，结果正确但白白多打一次网络）。对比 React：useEffect(fn, [hydrated]) 依赖手写死，改 plaza.sort 不会重跑——React 版天然没这问题。这正是「自动依赖收集」的双刃剑。
// 修法：untrack 把不想追踪的读取圈起来（本项目采用）
createEffect(() => {
  if (auth.hydrated) untrack(() => void fetchPlaza());  // effect 只订阅 auth.hydrated
});

4控制流：Show / For / Index

<Show>

callback 形式把 when 收窄为非空 Accessor：<Show when={auth.user}>{(user) => <Chip name={user().nickname}/>}</Show>，省去 ! 断言。

<For>

按元素引用协调，适合可增删的列表（广场、收藏）。

<Index>

按位置协调，item 是 Accessor、index 是数字，适合定长按位场景——CapsuleCodeInput 的 8 个格子用它最贴切。

5模块级 Signal / Store

Solid 的响应式不依赖组件树，「全局 store」就是模块顶层的 Signal/Store + 导出动作函数，角色等同 Zustand 但更轻——没有 create()、没有 selector、没有 Provider。四个 store：theme（createSignal）、auth/plaza/capsule（createStore）。

const [auth, setAuth] = createStore<AuthStore>({ user: null, hydrated: false });
export { auth };
export function setTokens(t) { setAuth({ user: t.user, ... }); persist(...); }
configureApi({ getAccessToken: () => auth.accessToken, ... });   // 注入 api client
createStore 的核心价值是路径更新 + 路径订阅：setPlaza({loading:true}) 顶层合并（items 引用不变 → 订阅 items 的 <For> 不重渲染）；setCapsule("mine","items", fn) 路径定位 + 函数式更新。序列号守卫 let fetchSeq = 0 刻意用闭包变量而非 store 字段——「把不该是响应式的东西放进响应式容器，是一种性能错误」。跨 store 联动 patchPlazaFavorited(...) 不需要 Context/Provider，直接函数调用。

6渲染原理：没有虚拟 DOM，更新去哪了

理解这一点能解释前面所有「为什么 props 不能解构」「为什么读值要调用函数」的根因。vite-plugin-solid 在编译期把 JSX 转成真实 DOM 创建 + 细粒度更新表达式：

<h3>{props.capsule.title}</h3>
// 编译成类似：
const el = document.createElement("h3");
insert(el, () => props.capsule.title);  // 包进 computation：title 变化时只重跑它，只改这个文本节点
组件函数只运行一次——职责是「建立 DOM 结构 + 注册细粒度 computation」，而非像 React 每次状态变化重跑、产出新 VDOM、再 diff。这就是为什么解构响应式数据会丢响应性：解构发生在那「唯一一次」执行里，拿到的是当时快照。更新是点对点的——setCount(5) 直接定位到订阅了 count 的那个节点去改，1000 行列表里改一个 item 标题，只有那一个 <h3> 被触碰。这是响应式模型谱系里「细粒度阵营」的极致。

7收藏按钮：乐观更新 + props 回灌

体现 Solid 响应式细节的最佳样本。持有本地 signal 做即时反馈，又要能接受外部（store patch / 详情页）的更新：

const [active, setActive] = createSignal(props.capsule.favoritedByMe);
// 关键：props 变化时把外部最新值「回灌」进本地 signal（组件被复用在列表里，父级 patch 后必须同步）
createEffect(() => {
  setActive(props.capsule.favoritedByMe);
  setCount(props.capsule.favoriteCount);
});

这个 createEffect 在 React 里对应「useEffect(() => setActive(props...), [props...])」，但 Solid 自动追踪 props.capsule.favoritedByMe，省去依赖数组。五栈同一个收藏按钮的接缝对比 →
