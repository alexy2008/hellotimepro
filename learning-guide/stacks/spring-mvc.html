@RestController 承载完整 JSON 契约；@Controller + Thymeleaf 承载 SSR 页面；HTMX 负责广场搜索/撤回等局部 HTML 替换；原生 JS 负责主题/头像/8 位码/AI/资料页 fetch 等浏览器行为；Spring Data JPA + Hibernate 负责双驱动持久化；CookieTokenFilter 把同源 cookie 自动转 Bearer。这是边界谱系右端「服务端模板 + 增强」的代表。

3HTMX：HTML 片段成为交互协议

HTMX 是 ~14 KB 的库（无构建、无 npm），用 HTML 属性（hx-get/hx-post/hx-target/hx-swap）触发 AJAX 并把响应 HTML 插入页面指定区域——不写 JS 就能局部刷新。广场搜索不返回 JSON 再拼 DOM，而是：

input/change（300ms 防抖）
↓
hx-get="/ui/plaza/grid" → FragmentController.plazaGrid()
↓
返回 "fragments/plaza-grid :: grid"（Thymeleaf 片段，只渲染那一块 HTML）
↓
HTMX 替换 #plaza-grid 区域

关键属性：hx-trigger="input changed delay:300ms"（防抖）、hx-target="#plaza-grid"（插入位置）、hx-sync="this:replace"（取消前一个同名请求）、hx-include="[name='q']"（带上搜索框值）。Playwright 陷阱：input 触发覆盖了 Playwright fill() 派发的 input 事件——若只写 keyup，自动化测试填值后不会触发搜索。

4CookieTokenFilter：cookie → Bearer 桥

契约要求 Bearer token，SSR 页面适合 httpOnly cookie。桥接规则：

若请求路径是 /api/v1/* 且没有 Authorization 头 且带 ht_access cookie
则包装请求，让 getHeader("Authorization") 返回 Bearer <ht_access>
因此：契约测试带真实 Bearer 时不受影响；无鉴权用例仍返回 401；浏览器同源 fetch 自动带 cookie 也能复用同一套 JSON 控制器。CookieAuthService 只在 access 缺失或过期时用 refresh 轮换，避免每次导航都 refresh 导致 token family 被误吊销（注释点名了 next/nuxt「急切刷新误登出」的坑）。这是cookie→Bearer 桥的 Servlet Filter 写法。

5收藏为何用同步 XHR（反直觉但正确）

广场搜索、撤回胶囊都走 HTMX 局部替换，唯独收藏刻意用同步 XHR。原因：收藏的典型操作是「点收藏 → 立刻导航到 /me/favorites」。若用异步请求，这次导航会 abort 掉尚未完成的收藏请求，事务来不及提交，跳过去就看不到刚收藏的那条。同步 XHR 阻塞到事务提交后才返回，保证后续导航能看到刚写入的数据。这是「不是所有交互都适合声明式局部刷新」的典型取舍，与 Rails 同源（收藏同步 XHR）。

6跨库 JdbcType 与 favorite_count 一致性

PG 用原生 uuid/timestamptz；SQLite 用 TEXT（32 位无横线 hex + 可排序 ISO-8601 文本）。差异集中在 CrossDbUuidJdbcType / CrossDbOffsetDateTimeJdbcType——是 Spring MVC 版对应 Ktor CrossDbColumns、Rails CrossDb、Laravel CrossDb 的实现（全栈跨库「Hibernate JdbcType」）。

FavoriteService 在事务内维护 favorite_count：添加锁胶囊 + 插入 + 递增；取消删除 + 递减（不低于 0）。PG 用 PESSIMISTIC_WRITE 行锁防并发漂移，SQLite 依赖单写事务。不要改成查询时 COUNT——spec 明确要求 denormalized favorite_count 被维护。
