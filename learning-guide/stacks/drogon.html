Drogon

C++20 协程 + 裸 SQL + 全文本协议绑定，十家里「最贴底层、最少依赖」的一个——把两个 C++ 协程真坑写成必读章节。

面向已熟悉 C++（类/模板/std::optional/智能指针/lambda）但没接触过 C++20 协程或 Drogon 的读者。整理自 backends/drogon/TECHNICAL_GUIDE.md（454 行）。UUID 是手写的、JWT 是 OpenSSL HMAC 拼的、bcrypt 是复制进来的源码、跨库差异靠纯文本协议抹平——代价是样板多、踩坑深，回报是没有任何隐藏魔法。

1技术选型与理由

Drogon 1.9 · FetchContent 静态链接

C++ 生态最成熟的异步 HTTP 框架，自带 ORM/HttpClient/协程。brew 无 formula，用 FetchContent 锁定版本可复现。首次编译 4-5 分钟（编 drogon 本体）。

裸 SQL（不用 Mapper<T>）

Mapper<T> 模板对跨库双驱动反而碍事；execSqlCoro + 手写 SQL 与其它栈一致。

C++20 协程

回调金字塔在 10+ 步的事务流程里不可维护；Task<>/execSqlCoro 已成熟。refresh 轮转有 6+ 步，几乎不可能用回调写。

OpenBSD bcrypt（third_party）

C++ 无标准 bcrypt；复制本仓库 nest 后端 node_modules/bcrypt 的 ISC 许可源码，零新增外部依赖。

2整体地图与请求流向

Trantor 事件循环（多 IO 线程）→ 协程 handler lambda（co_await guarded([&]{ ... })，auth_context::requiredUser 解析 Bearer、requireJsonBody 取参）→ services.cc 协程（co_await state->db->transaction()）→ repos.cc → db.cc（co_await execSqlCoro，一份 SQL 文本协议绑定）→ PG（池 8）或 SQLite（单连接，天然串行）。

3C++20 协程 + Drogon 的三件事

机制一Task<T> 与 co_await：为什么用协程不用回调

co_await 一个 Task<T> 就拿到结果 T，写法和同步代码一样直；底层是「挂起当前协程、IO 完成后在事件循环线程恢复」。没有协程，「查用户 → 验密码 → 插 token → 提交」要写成四层嵌套回调（callback hell），refresh 轮转 6+ 步几乎不可维护。

机制二guarded()：协程版的「异常 → 错误外壳」

C++ 没有 Rust 的 IntoResponse、也没有 Spring 的 @RestControllerAdvice。用模板函数 guarded() 充当统一异常出口，所有 handler 主体都套在里面：ApiError → 对应状态码，DrogonDbException / std::exception → 500（写 LOG_ERROR，不泄漏崩溃栈）。

机制三handler = 协程 lambda + shared_ptr<AppState> 注入

每个路由是返回 Task<HttpResponsePtr> 的 lambda，按值捕获 state，主体套 guarded()。固定套路：取参 → 调 service → envelope::ok 包壳。jsoncpp 的 Json::nullValue 序列化就是字面 null，天然满足契约的显式 null。

4文本协议跨库（db.cc）

与 Axum 的 Value/Cell 枚举不同，这里更激进：绑定参数全部是 std::string。

语义类型绑定文本PG 行为SQLite 行为
UUIDPG 带横线 / SQLite 32-hex列上下文推断为 uuidTEXT 直存
时间戳…T….SSSSSS+00:00（双驱动同格式）timestamptz 文本解析TEXT 直存（与 seed 逐字符一致）
布尔'1' / '0'boolean 接受 0/1INTEGER 亲和性
变参分发 switch (params.size())：execSqlCoro 是变参模板，运行时的 std::vector<std::string> 无法直接展开成可变模板实参——Db::query 用 switch 0..16 逐档手动展开（当前最大用量 10，上限 16 按需扩档）。UUID 是手写的：arc4random_buf 取 16 字节、手动置 version 4 / variant 位、snprintf 成串。这是双库三解法的「C 类」最激进的一版。

5事务：异步析构提交的坑（必读）

drogon Transaction 的提交时机是最后一个 shared_ptr 析构时异步发送 COMMIT。直接依赖析构会出现：响应已发出 → 客户端立刻发下一请求 → PG 连接池（8 连接）把它路由到另一条连接 → 刚写的数据还没提交，读不到。本实现首轮 PG 契约就撞上了（register 后随即 401、创建后搜索不到，且两次失败点不同——典型竞态特征）。

struct CommitAwaiter : drogon::CallbackAwaiter<bool> {
    void await_suspend(std::coroutine_handle<> handle) {
        trans_->setCommitCallback([this, handle](bool committed) {
            setValue(committed);   // 把提交结果回传给 co_await
            handle.resume();       // 在提交回调里唤醒协程
        });
        trans_.reset();            // 释放最后引用 → 析构发 COMMIT → 触发上面的回调
    }
};
关键顺序是先挂回调、再 reset：reset 释放掉最后一个事务引用触发析构发 COMMIT，COMMIT 落地后回调 handle.resume()，co_await awaitCommit(...) 之后的代码才继续——把「不可控的异步析构提交」改造成「可 await 的提交」，回到和其它栈一致的「提交完成才返回」语义。三个纪律：① catch 里必须 rollback（析构语义是 commit）；② co_return 不能写在 try 里；③ awaitCommit 必须 move。这是全项目最有价值的语言级战例。

6C++ 协程限制：catch 里不能 co_await

语言规定 catch handler 内禁止 co_await。所有「失败后异步补救」都要改写成「catch 记 flag，try 外 co_await」——本实现有三处：LLM auto 风格回落 chat、chat 的 thinking 字段 400 重试、postJson 的退避重试。事务的 rollback() 是同步方法所以不受限（这也是 §5 里 catch 能直接 rollback 的原因）。

7全手写安全原语（security.cc）

JWT HS256（OpenSSL HMAC）

签发约 20 行。校验顺序：三段形态 → CRYPTO_memcmp 常数时间比签名（防时序侧信道）→ 解析 payload → 检查 exp。过期 access_token_expired、其余 invalid_token。

bcrypt（third_party）

调 third_party/openbsd_bcrypt，cost 10、'b' 变体，arc4random_buf 取盐；验证前先做形态防御再 CRYPTO_memcmp 常数时间比对。

base64url 也是手写的

security.cc 末尾自带 base64url/base64urlDecode（URL 安全字母表、无 padding），供 JWT 三段和 refresh token 共用——又一处「不引库、摊在明面上」。

third_party/openbsd_bcrypt 来历透明：三个文件原样复制自本仓库 backends/nest/node_modules/bcrypt/src/——即 npm bcrypt 包内嵌的 OpenBSD 实现（Niels Provos 原版，ISC/BSD 许可，保留原始版权头）。理由：已在依赖树内、nest 用它通过过同一套契约、零新增外部来源。
