1技术选型与设计特色

Nuxt 3 + Nitro

文件系统路由；pages/ = UI，server/api/v1/ = REST API。

混合渲染（核心卖点）

routeRules 把 /create、/me/** 标为 ssr:false（SPA 孤岛），其余走 SSR。

Drizzle ORM · 双 schema

与 Next 全栈几乎同一份代码——刻意对照，「差异只是路径」。

自动导入

代码里不用写 import { ref } from 'vue'、import { useAuthStore }——Nuxt 构建时自动扫描注入。

2按角色分目录（与 Next 完全不同）

Next 是「按 URL 分目录」，Nuxt 是「按角色分目录」——pages/、layouts/、components/、composables/、stores/、middleware/、plugins/、server/ 每个目录被 Nuxt 自动识别为对应角色。

fullstacks/nuxt/ ├── app.vue # 应用根：只 5 行 <NuxtLayout><NuxtPage/></NuxtLayout> ├── pages/ # 文件系统路由：pages/login.vue → /login ├── layouts/ # 通过 definePageMeta 选择 ├── components/ composables/ stores/ # 全部自动导入 ├── middleware/auth.client.ts # 路由守卫（注册名 auth-client） ├── plugins/bootstrap.client.ts # 客户端启动钩子 └── server/ # ★ 这里就是「后端」（目录级隔离） ├── api/v1/*.<method>.ts # 文件 = 端点，后缀决定 HTTP 方法 ├── lib/ services/ db/ # 仅 Nitro 可达

app.vue 取代了 Vue3 SPA 的 index.html + main.ts + App.vue + router/index.ts 四份文件。server/ 目录天然隔离——永远不会被打进客户端 bundle，等价 Next 的 import "server-only"，但是目录级、不需每个文件加导入。

3Nitro：Nuxt 的后端引擎

Nitro 给 Nuxt 提供 server/api/** 路由扫描（文件名后缀 .get.ts/.post.ts 决定 HTTP 方法）、中间件、启动钩子，以及一组基于 h3 的事件对象 API（defineEventHandler、getRouterParam、readBody、setResponseStatus…）。

// server/api/v1/health.get.ts → GET /api/v1/health
export default defineEventHandler((event) =>
  withApi(event, () => ({ status: "ok", ... })));
与 Next 的请求/响应模型对照：Next Route Handler 用 Web 标准 Request/Response；Nitro 用 h3 event 对象（getXxx(event) helper、setResponseStatus(event, ...)）。一个文件一个方法（me.get.ts、me.patch.ts 分两文件，Next 是单文件多导出）。生产构建打包成单一 .output/server/index.mjs，nitro.preset 可切 Node / Vercel / Cloudflare / Lambda / static。

4自动导入

Nuxt 最有辨识度的「魔法」：Vue API（ref/computed/watch）、Pinia stores、components、composables、Nuxt helpers（useRoute/navigateTo/definePageMeta）、h3/Nitro 助手全部自动导入。实际项目里 pages/index.vue 脚本块只 import 了 vue 和 pinia，其余全是自动导入。

5混合渲染与 useAsyncData（最值得理解）

本实现相对纯 SPA 的核心增量。ssr: true 让所有页面默认 SSR，再用 routeRules 把鉴权/强交互页退回客户端：

routeRules: {
  "/create": { ssr: false },   // 依赖 localStorage 登录态，SSR 无收益且会误重定向
  "/me/**": { ssr: false },
}
useAsyncData 服务端取数：SSR 时回调在服务端跑，$fetch('/api/v1/*') 由 Nitro 同进程内直接调用处理器（无真实 HTTP 往返），首屏 HTML 带数据；数据序列化进 payload，客户端 hydrate 复用、不重取。鉴权投影 favoritedByMe：SSR 无 token → 一律 false，登录用户在 onMounted 里带 token 补取纠正。这是边界谱系左端「同构」的 Vue 版。

6招牌坑：.client.ts 对路由中间件不生效

路由中间件不认 .client / .server 后缀。middleware/auth.client.ts 看起来像「只在客户端跑的守卫」，但 Nuxt 只把它注册成名为 auth-client 的普通命名中间件，服务端和客户端都会执行。后果：若受保护页开了 SSR，守卫在服务端运行、读不到 localStorage 登录态 → 把已登录用户误判为未登录、重定向 /login。对策：用 routeRules 把这些页标 ssr:false，守卫自然只在客户端跑。.client 后缀对 plugins/components 有效，对中间件无效。

7hydration 守卫

服务端没有 window/document/localStorage，两类代码必须隔离否则 SSR 500：

<ClientOnly> 包裹

依赖 localStorage 的渲染（登录态决定的 Header 菜单、主题）。服务端一律按「未登录/默认主题」渲染，避免 hydration mismatch。

import.meta.client 守卫

触碰 window/document 的副作用。注意 watch(..., {immediate:true}) 的回调会在 SSR 的 setup 阶段同步执行——不能假设「watcher 只在客户端跑」。

另一坑：SSR 取数不要用 api/client.ts（原生 fetch + BASE=""，相对 URL 在服务端无 origin 会抛 Failed to parse URL），统一用 Nuxt 的 $fetch（ofetch，服务端直达 Nitro）。
