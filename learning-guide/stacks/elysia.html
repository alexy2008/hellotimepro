1技术选型与设计特色

Bun + Elysia · 轻运行时与轻框架

依托 Bun 原生 TS 运行时与内置 HTTP，Elysia 用链式 API 显式注册路由，样板代码很少，启动不需要单独编译。

TypeScript + Zod · 显式边界校验

不用 Elysia 自带 t schema，统一走 Zod parse(...)——便于转成统一 details 结构，也与 Nuxt 全栈对齐。

双库方言 + 原生 SQL

摒弃重量级 ORM，用 pg + bun:sqlite，靠 query/one/tx 三个原语封装占位符适配、连接池和事务。

轻量函数式分层

不是严格四层架构，而是 Elysia 风格：main.ts 路由、services/ 按域拆规则、db.ts 只管连接/查询/事务。

2整体地图与请求流向

请求经 Bun.serve（Elysia 封装）→ 路由匹配 method+path → main.ts 的 route(...)/routeEmpty(...)（读 body/params/query/headers、Zod parse 校验、requireClaims/readClaims 解析 Bearer）→ services/* → db.ts 的 query/one/tx。

3目录结构

backends/elysia/src/ ├── main.ts # Elysia 入口、路由注册、静态资源 ├── config.ts # 环境变量 → env 对象 ├── db.ts # 连接、占位符适配、事务封装 ├── services/{auth,capsules,plaza,favorites,ai}.ts # 按域拆分（已重构出模块） ├── security.ts # JWT、密码哈希、refresh token 原语 ├── validation.ts # Zod 请求 schema ├── envelope.ts errors.ts # 统一响应壳 + ApiError └── types.ts # 数据库行 → 响应 DTO 映射

4Elysia 的几个关键机制

路由上下文

handler 收到 { set, body, params, request }。set.status 设状态码，查询参数直接用标准 new URL(request.url).searchParams。

显式包装响应

route(set, fn, 200) 成功包成统一 envelope；routeEmpty(fn, 204) 返回空 body；两者都捕获异常交给 errorResponse。

校验用 Zod

统一 parse(registerSchema, body)。safeParse 适合转成 details:[{field,message}]，复杂规则（Unicode 正则/密码强度）更直观。

.post("/api/v1/capsules", ({ set, body, request }) =>
  route(set, async () => {
    const claims = await requireClaims(request.headers);    // ① 要求登录
    return createCapsule(claims.id, parse(createCapsuleSchema, body));  // ② 校验 ③ 调 service
  }, 201),                                                  // ④ 包成 201

5原生 SQL 与方言适配：db.ts

db.ts 做三件事：建连接（PG 用 pg.Pool、SQLite 用 Bun 内置 Database + PRAGMA）、提供 query/one、提供事务 tx。Bun 的 bun:sqlite 是同步、pg 是异步，db.ts 把两者都包成 async 让 service 不关心差异。

占位符适配：业务层统一写 ? 占位符，SQLite 原生接受、PG 需要 $1/$2。pgSql() 在执行前自动把 ? 替换成 $n，service 的 SQL 不必写两遍。这是双库三解法里的「C 类 · 一份 SQL + 自建值编解码」。

6事务与收藏一致性

收藏计数必须和 favorites 行保持一致，所以 addFavorite/removeFavorite 必须在事务里执行。两库不同写法：

// PostgreSQL：拿连接 → BEGIN → ... → COMMIT，并 SELECT ... FOR UPDATE 锁胶囊行
// SQLite：sqlite.exec("BEGIN IMMEDIATE")  ——尽早拿写锁，适合短事务，避免并发读到过期计数

关键规则：只能收藏 in_plaza=true 的胶囊；不能收藏自己的（400 BAD_REQUEST）；重复收藏幂等（200 且计数不增）；取消幂等（未收藏也 204）。

7鉴权与 refresh 轮转

access token 用 jose 签 JWT HS256；refresh token 是随机 256-bit base64url，数据库只存 SHA-256 哈希。readClaims（登录可选，无 token 返回 null、非法返回 401）用于广场/按码查询；requireClaims（必须登录）用于 /me/* 和创建。

对 raw token 做 SHA-256，查 refresh_tokens.token_hash
2
不存在或过期 → 401
3
已 revoked → 重放 → 撤销同 family_id 下所有未撤销 token → 401
4
有效 → 撤销旧 token，签发新 access+refresh，保留同一 family_id

8为什么这里没有 ORM

选择原生 SQL + 小型方言适配（而非 Drizzle/TypeORM），是为了展示 Bun/Elysia 下更轻的写法：SQL 与字段映射清晰可见、事务和锁语义显式（尤其适合解释 favorite_count 一致性）、业务只依赖 query/one/tx 三原语。

代价：SQL 字段映射要手写，如 owner_id AS "ownerId"、favorite_count AS "favoriteCount"。这类映射必须谨慎维护，否则 TypeScript 类型看起来正确、运行时字段可能是 undefined。
