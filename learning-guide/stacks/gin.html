Gin

极简、显式、无魔法：错误一律 if err != nil，所有控制流摆在明面上，编译成单一静态二进制、零运行时依赖。

1技术选型与设计特色

Go + Gin · 高并发与极速路由

利用 Goroutine 与原生高并发优势，配合 Gin 轻量级 HTTP 路由与中间件链，实现极低延迟与优异吞吐。gin.Engine 就是 http.Handler，Gin 没有自己的 server。

GORM · 简洁 ORM

通过结构体标签（Struct Tags）实现表关系映射与自动数据映射，大幅简化持久化代码。本项目不依赖 AutoMigrate，schema 以 spec/db 为准。

双库自适应 + 二进制构建

SQLite 模式对路径与锁行为精细设计；Go 编译后形成单一二进制，运行时不依赖框架命令——冷启动极快、零运行时依赖。

清晰四层 · 显式分层

internal/ 划分 config / core / model+db / dto / service / handler / middleware，严格展示与业务分离。

2整体地图与请求流向

每个连接一个 goroutine → Gin 按 URL/方法匹配路由 → 中间件链 Logger → Recovery → CORS →（RequireAuth/OptionalAuth）→ handler（ShouldBindJSON 反序列化+校验、CurrentUser(c) 取用户）→ service → GORM → 驱动。出错统一走 middleware.RespondErr(c, err)，按 APIError.StatusCode 输出错误外壳。

4Gin 的三个核心机制

机制一路由分组（Group）

Group 返回的还是能挂中间件、注册路由的对象，公共前缀与中间件一次配齐。三组鉴权策略不同：/auth 公开、/capsules 与 /plaza 用 OptionalAuth（登录可选，影响 favoritedByMe）、/me 用 RequireAuth（必须登录）。

机制二中间件链与 *gin.Context

中间件就是 func(*gin.Context)。*gin.Context 是 Gin 的灵魂，把 request/response/URL 参数/JSON 反序列化/KV 上下文都包成一个对象。c.Set/c.Get 让中间件与 handler 共享数据；c.Abort()/c.Next() 控制责任链。

func RequireAuth(db *gorm.DB) gin.HandlerFunc {
    return func(c *gin.Context) {        // 闭包捕获 db
        token := parseBearer(c)
        if token == "" { RespondErr(c, core.UnauthorizedErr(...)); c.Abort(); return }
        c.Set(CtxUser, &user)            // 写进当前请求的 KV 上下文
        c.Next()                         // 继续往下
    }
}
机制三参数绑定 ShouldBindJSON + struct tag

做两件事：用 encoding/json 按 json: tag 反序列化；用 validator/v10 跑 binding: tag 校验。一律用 ShouldBindXxx 而非 BindJSON——后者会自动写 400 响应，与统一错误包装冲突。

type RegisterRequest struct {
    Email    string `json:"email"    binding:"required,email,max=254"`
    Password string `json:"password" binding:"required,min=8,max=128"`
}

5GORM 与一个隐蔽的坑

常见调用模式：db.First 单行、db.Create 插入、UpdateColumn(... gorm.Expr("favorite_count + 1")) 原子自增、db.Transaction(func(tx){...}) 事务、clause.Locking{Strength:"UPDATE"} 行锁（仅 PG）、clause.OnConflict{DoNothing:true} 幂等收藏。进了事务闭包必须用 tx 而非 db。

SQLite URL 解析坑（教学价值高）：sqlite:////abs/path.db（4 个 /）会被解析成把 /abs/path 和 //abs/path 当成两个数据库做锁协调，结果 INSERT 落一个锁域、SELECT 落另一个——表现为「注册成功，但所有登录接口都说用户不存在」。解析 URL 时不能想当然依赖标准库，特别是涉及驱动底层行为时。

6错误：显式返回而非异常

Go 没有异常，业务错误用「自定义 error 类型 + 显式返回」。统一 APIError（Code/Message/StatusCode/Details），业务层 return nil, core.NotFoundErr(...)，handler 拿到 err 后 RespondErr(c, err) 用 errors.As(err, &apiErr) 类型断言：是 *APIError 就用它的字段，不是就降级 500。

Go 风格：错误是返回值不是异常，永远不要忽略 err——本项目里 _ = c.ShouldBindJSON(&req) 这种忽略是因为 logout 请求体允许为空，是经过思考的取舍。

7DTO：泛型 Envelope 与指针区分 null

用 Go 1.18+ 泛型：Envelope[T any]、Paginated[T any]。可选字段用 *string/*time.Time——nil 序列化成 null，零值会写出 "" 或 "0001-01-01T00:00:00Z"，必须用指针区分「没传」和「显式空」。字段嵌入（embedded struct）既共享字段也共享 JSON 序列化，自动平铺。

8refresh 轮转的事务语义

Refresh 是最复杂的一段。事务里的提交语义：闭包返回 nil 提交、返回 err 回滚。重放分支故意返回 nil，把 family revoke 提交掉，再在外层把 replayErr 当返回错——这样 401 响应和「整族作废」同时生效。

err := db.Transaction(func(tx *gorm.DB) error {
    if config.App.DBDriver == "postgres" {
        q = q.Clauses(clause.Locking{Strength: "UPDATE"})   // 仅 PG 行锁
    }
    if rt.RevokedAt != nil {            // 重放检测 → 整族作废
        tx.Model(...).Where("family_id = ? AND revoked_at IS NULL", rt.FamilyID).Update(...)
        replayErr = core.UnauthorizedErr(...); return nil   // 返回 nil 让事务提交
    }
    res := tx.Model(...).Where("id = ? AND revoked_at IS NULL", rt.ID).Update(...)
    if res.RowsAffected != 1 { ... }    // 乐观并发：被抢先 revoke → 整族作废
})
乐观并发：UPDATE … WHERE id = ? AND revoked_at IS NULL 加 RowsAffected != 1 检查，比读-改-写更可靠，PG/SQLite 通用。这是事务四流派里的「③ outcome 模式」。

9并发原语

sync.Map + sync.Mutex

登录失败限流：sync.Map 存 email→桶，桶内 sync.Mutex 保护时间戳切片，60s 滑动窗口。

sync.Once

头像目录用 sync.Once.Do(fn) 保证全程只加载一次、并发安全，比 init() 灵活（可延迟到首次访问）。

包级 HTTP Client

LLM 客户端用包级单例 &http.Client{Timeout:30s} 复用连接池。生产中绝不要裸用 http.DefaultClient（无超时）。
