1技术选型与设计特色

ASP.NET Core · 中间件管线 + DI

Program.cs 显式组装服务、DbContext、中间件、静态资源和 Controllers，展示 .NET 现代最小宿主模型。

Controllers · 清晰 HTTP 边界

每个控制器负责一组 API，继承 ApiControllerBase 获得统一响应包装、鉴权 header 读取、query 参数解析。

EF Core · LINQ + 变更跟踪

Repository 用 EF Core 表达查询和事务，保留 C# 类型系统优势，同时不让 EF 创建/迁移 schema。

跨库 ValueConverter + 手写校验

SQLite 的 UUID/时间戳格式由 CrossDb 接管；禁用 [ApiController] 自动 400，按契约统一返回 422。

2整体地图与请求流向

Kestrel → ErrorHandlingMiddleware（最外层）→ Controller action（继承 ApiControllerBase，AuthContext.Required/Optional 解析用户、Validation 手写校验）→ Service（scoped）→ Repository（EF Core / LINQ / FromSqlRaw）。返回用 Wrapped(...) 包统一壳。

4五个核心机制

机制一DI 生命周期：singleton vs scoped

AddSingleton 全进程一个实例（SecurityService 无状态、AvatarService 启动加载一次、LoginRateLimiter 进程内计数必须单例）；AddScoped 每请求一个实例（AppDbContext 与所有用它的仓库/服务都 scoped，一次请求共享同一 DbContext）。把限流器错放 scoped、或把 DbContext 错放 singleton 都会出 bug——.NET DI 最常见的坑。

机制二中间件管线：洋葱模型

app.UseXxx(...) 按顺序构成洋葱，请求自外向内、响应自内向外。ErrorHandlingMiddleware 放最外层，能 try/catch 住内层抛的任何异常，转成契约错误外壳。

机制三控制器薄、基类兜底

公共能力上提到 ApiControllerBase：Wrapped<T>（统一成功壳）、AuthHeader、IntParam/Page/PageSize（缺失用默认、存在但非整数 → 422）。[FromBody] ... ? 用可空 + ?? new(...)，把空请求体交给手写校验裁决成 422 而非框架自动 400。

机制四EF Core 变更跟踪：改对象就是改库

EF 跟踪从 DbContext 取出的实体，SaveChangesAsync() 时把改过的字段生成 UPDATE。收藏计数写成 capsule.FavoriteCount += 1（行锁保护下的读-改-写）。与 axum/gin 的「原子 SQL 表达式」是两种风格，都能保证并发正确——前者更 OO、后者省一次读。

机制五禁用自动 400

SuppressModelStateInvalidFilter = true 关掉 [ApiController] 在 ModelState 无效时的自动 400，改用手写 Validation.cs 统一返回 422 + 自定义 details。

5跨库 ValueConverter（最值得读）

问题背景：EF Core SQLite 默认把 DateTimeOffset 存成空格分隔 + 7 位小数的 TEXT，会破坏 open_at <= now 和 ORDER BY created_at 的字符串比较——必须接管格式。

public static string FormatTimestamp(DateTimeOffset value) {
    var u = value.ToUniversalTime();
    var s = u.ToString("yyyy-MM-ddTHH:mm:ss", InvariantCulture);
    long frac = u.Ticks % TicksPerSecond;
    if (frac != 0) s += "." + frac.ToString("D7").TrimEnd('0');  // 零小数不输出
    return s + "+00:00";                                         // 与 seed 对齐：+00:00 而非 Z
}
GuidToHex = new(g => g.ToString("N"), s => ParseGuid(s));        // 仅 SQLite 挂
ApplySqliteConverters() 仅在 SQLite 下把转换器挂到每个 Guid/时间戳属性；PostgreSQL 不挂，交给 Npgsql 原生映射。这是对 Ktor CrossDbColumns / Spring @JdbcType 的 EF Core 等价实现（双库三解法「A 类」）。

6Service 层与事务

FavoriteService 维护计数：BeginTransactionAsync → FindByIdForUpdate（PG 拼 FOR UPDATE 行锁）→ 幂等检查 → capsule.FavoriteCount += 1（EF 变更跟踪）→ SaveChangesAsync → CommitAsync。

refresh 轮转用 Outcome { Success, Invalid, Reused } 枚举：事务内只设 outcome、CommitAsync()，出事务后 switch 转 401——等价 Ktor/Spring 的 noRollbackFor 语义（事务四流派 ③）。另一个 .NET 坑：EF 插入排序——用 HasForeignKey 声明 FK 依赖，让 EF 一次 SaveChanges 同插 user + refresh_token 时先插 user。

7鉴权与两个 .NET 特有坑

// ① Microsoft.IdentityModel 强制 HS256 密钥 ≥256 位 → 用 SHA-256 把任意 secret 派生成 32 字节
_key = new SymmetricSecurityKey(SHA256.HashData(Encoding.UTF8.GetBytes(config.JwtSecret)));
_validation = new TokenValidationParameters {
    IssuerSigningKey = _key,
    ClockSkew = TimeSpan.Zero,   // ② 关掉默认 5 分钟过期宽限——契约「过期即失效」需要精确边界
};

校验区分异常：SecurityTokenExpiredException → access_token_expired，其它 → invalid_token。这类「框架约束 vs 契约要求」的调和是高质量教学点。
