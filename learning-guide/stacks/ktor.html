1技术选型与设计特色

Ktor · 插件式轻量框架

不像 Spring 那样大规模自动装配，功能通过 install(ContentNegotiation)/install(StatusPages)/routing{...} 显式组合，适合展示「轻量 JVM 服务」。

Kotlin · 强类型 + 简洁

DTO 用 @Serializable data class，nullable 类型直接反映字段可选性，service 代码比 Java 更紧凑。

Exposed · 类型安全 SQL DSL

仓库层用 Kotlin DSL 表达查询/排序/事务，列名拼错在编译期报错，不走 JPA 实体生命周期。

手动依赖装配 · AppComponents

明确 new 出 repository/service，不引入 DI 容器——依赖关系一眼可读，适合教学。

2整体地图与请求流向

Netty → Application.module()（ContentNegotiation/CORS/StatusPages）→ routing（call.receive<T>() 反序列化、AuthContext 解析 Bearer）→ service → repository（Exposed DSL）。返回 call.ok(...) 包统一壳，异常抛 ApiException 由 StatusPages 转错误外壳。

ContentNegotiation 关键配置 explicitNulls = true——让 message/errorCode/content 等 null 字段显式输出 null（契约用 strict equal 断言这些键存在）。

4Ktor / Exposed 的四个核心机制

机制一插件 install 显式组合

Ktor 没有「自动配置」——每个能力都靠 install(...) 显式装上，启动路径一眼可见。与 Spring「约定大于配置 + 自动装配」是两种哲学：Ktor 把组合权交给你，代价是要自己写、回报是没有隐藏行为。

机制二路由薄、call.ok 包壳、intParam 卡分页

每个端点保持很薄：取参 → 调 service → 包壳。鉴权不是中间件而是显式第一行 required(...)/optional(...)。分页用手写 intParam()：缺失用默认、传非整数则抛 VALIDATION_ERROR。

post("/api/v1/capsules") {
    val user = c.authContext.required(authHeader(call))   // 鉴权显式第一行
    call.ok(c.capsuleService.create(user, call.receive<CreateCapsuleRequest>()), Created)
}
机制三挂起事务 dbQuery {}

Exposed 事务在协程里用 newSuspendedTransaction(Dispatchers.IO)，封装成 dbQuery {}。纪律：每个 service 公共方法只调用一次，保证多步操作在同一事务里原子提交——block 正常返回即 COMMIT、抛异常即 ROLLBACK。

机制四Exposed DSL：类型安全 SQL

列名是强类型对象（Capsules.id、Capsules.favoriteCount），拼错/类型不符在编译期报错。原子自增用 it[favoriteCount] = favoriteCount + 1，行锁用 q.forUpdate()（仅非 SQLite 方言）。

5跨库列类型（最值得读）

CrossDbColumns.kt 自定义两个 ColumnType，在同一套表定义上按方言分流读写格式：

class CrossTimestampColumnType : ColumnType() {
    override fun sqlType() = if (isSqliteDialect) "TEXT" else "TIMESTAMP WITH TIME ZONE"
    override fun notNullValueToDB(value: Any): Any {
        val odt = (value as OffsetDateTime).withOffsetSameInstant(ZoneOffset.UTC)
        return if (isSqliteDialect) odt.format(WRITE) else odt   // SQLite 写 ISO TEXT，PG 直传
    }
    // WRITE：输出秒+可选小数秒，零偏移渲染成 +00:00（而非 ISO 默认的 Z），与 seed 对齐
}
PG 用原生 uuid/timestamptz；SQLite 存 32 位 hex TEXT + ISO TEXT，写出格式与 seed 逐字符对齐（T 分隔、+00:00），保证「字符串比较即时间比较」。这是双库三解法「A 类」，手册点名它对应 Spring @JdbcType、ASP.NET ValueConverter——跨栈引用的范例。

6挂起事务与一致性

favorite_count 必须和 favorites 表同事务更新：PG 路径用 SELECT ... FOR UPDATE 锁胶囊行，SQLite 依赖单写事务和连接池大小 1（maximumPoolSize = 1，避免「database is locked」——等价 Vapor 的 AsyncGate、Axum 的池上限 1）。

refresh 轮转用 outcome 模式（RefreshOutcome sealed interface）：事务内不抛业务错，旧 token 被重放时先提交同 family 吊销、再返回 401——dbQuery 提交后外层 when(outcome) 才把 Reused/Invalid 转成 401。对应 Spring 的 noRollbackFor 思路（事务四流派 ③）。

7鉴权与安全

SecurityService 用 java-jwt（auth0）+ favre bcrypt。解码区分两个 message：TokenExpiredException → access_token_expired，其余 JWTVerificationException → invalid_token（契约区分）。refresh token 用 SecureRandom 取 32 字节 → base64url，落库只存 SHA-256 hex。AuthContext 是 Web 边界，业务 service 不直接读 HTTP header（presentation 与 application 分离）。

8从真实请求读代码：注册

① 校验（Validation）缺字段/格式错抛 ApiException → StatusPages 转 422
↓
② dbQuery {} 一次挂起事务
↓
③ 唯一性预检 existsByEmail / existsByNickname
↓
④ security.hashPassword（bcrypt）⑤ users.insert（Exposed）
↓
⑥ issueTokenPair 签发并落库 refresh token
↓
⑦ block 正常返回 → COMMIT；抛 ApiException → ROLLBACK → call.ok(..., Created)
事务边界由 dbQuery {} 一行划定，比手写 BEGIN/COMMIT 干净
一处取舍：bcrypt 在 dbQuery 闭包内调用——它是 CPU 密集操作（cost 10 约几十毫秒），握着连接做哈希会拖长持锁时间。与 Axum/Vapor/Drogon「bcrypt 放事务外」略不同，教学项目可接受，生产可前移。
