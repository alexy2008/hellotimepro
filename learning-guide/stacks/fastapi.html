1技术选型与设计特色

FastAPI · 类型化 Web 框架

本实现采用同步路由函数与同步 SQLAlchemy Session，突出依赖注入、Pydantic 边界校验、自动 OpenAPI 文档，而非演示 async 数据访问。搭配 Uvicorn 运行，天然集成 Swagger UI（/docs）。

Pydantic · 严格输入校验

接口边界上的输入输出完全用 Pydantic Schema 声明与校验。在请求到达业务逻辑前即完成字段校验与类型转换，提供安全可靠的类型安全边界。

SQLAlchemy · 双数据库引擎

配置跨驱动连接池与方言支持，后端无需改任何核心代码，即可通过环境变量在 PostgreSQL 与 SQLite 间无缝切换。

四层架构 · 分层解耦

严格遵循呈现层 → 应用层 → 领域层 → 基础设施层。路由（Routers）/ 校验（Schemas）/ 业务（Services）/ 模型（Models）各司其职。

2先建立整体地图

FastAPI 后端的职责是提供 /api/v1/* HTTP API、校验请求数据、处理鉴权（JWT access token + refresh token 轮转）、读写四张表、保证返回格式符合 spec/api/openapi.yaml。

一个关键认知：业务代码不直接返回错误 JSON。业务层只 raise APIError，真正把异常变成 HTTP 响应的是 main.py 里的 exception handler——业务层只表达「发生了什么业务错误」，入口层统一决定「怎么变成 API 响应」。

3一个请求的流向

路由层把 HTTP 世界翻译成 Python 函数调用：Schema 先校验、Depends 注入 db/user、再调 service

4目录结构

backends/fastapi/ ├── app/ │ ├── main.py # FastAPI 应用入口（CORS / 路由 / 异常处理） │ ├── deps.py # Depends 依赖：数据库、当前用户 │ ├── api/v1/ # 路由层：定义 URL 和 HTTP 方法 │ ├── schemas/ # Pydantic DTO：请求/响应数据结构 │ ├── services/ # 业务层：注册、胶囊、收藏、广场… │ ├── models/ # SQLAlchemy ORM 模型：数据库表的 Python 表达 │ ├── db/ # engine、session、跨驱动类型 │ └── core/ # 配置、错误、安全工具 ├── alembic/ # Alembic 迁移参考（run 不自动执行） ├── tests/ # pytest 测试（986 行） └── run / build / test # 三件套脚本
run 脚本会：① uv sync 装依赖；② SQLite 默认用 data/sqlite/hellotime.db；③ 把普通 PG URL 标准化为 postgresql+psycopg://；④ uvicorn app.main:app 启动。注意：run 不建表、不执行 Alembic、不 seed，数据库生命周期一律交给根目录 scripts/db。

5分层详解

路由层 app/api/v1 —— 把 HTTP 翻译成函数调用

聚合入口 api/v1/__init__.py 用 APIRouter(prefix="/api/v1") 把各模块接进来。路由函数只做三件事：接收参数 → 调 service → 包成 Envelope。以注册为例：

@router.post("/register", response_model=Envelope[AuthTokens], status_code=201)
def register(req: RegisterRequest, db: Session = Depends(get_db)) -> Envelope[AuthTokens]:
    tokens = auth_service.register(db, email=req.email, password=req.password,
                                   nickname=req.nickname, avatar_id=req.avatarId)
    return Envelope(success=True, data=tokens)

req: RegisterRequest 自动把 body 解析成 Pydantic 模型并校验；Depends(get_db) 注入 session；response_model 声明响应模型供文档与序列化。

Schema 层 app/schemas —— 接口边界的数据结构

「输入输出的类型说明 + 校验规则」。字段缺失 / 类型错 / 不满足规则时，路由函数根本不会执行，FastAPI 抛 RequestValidationError 再被 main.py 转成统一错误。复杂校验用 @field_validator：

class RegisterRequest(BaseModel):
    email: EmailStr
    password: str = Field(min_length=8, max_length=128)
    nickname: str = Field(min_length=2, max_length=20)
    avatarId: str = Field(min_length=2, max_length=20)

    @field_validator("password")
    @classmethod
    def _password_policy(cls, v): ...  # 至少 8 位且含字母和数字
ORM 模型 app/models —— 数据库表的 Python 表达

把表映射成 Python 类。关键分工：models 描述「数据库长什么样」，schemas 描述「API 输入输出长什么样」，二者不混淆——API 可隐藏字段（未开启胶囊不返回 content），但数据库仍保存完整正文。

模型表作用
Userusers用户账号、昵称、头像
Capsulecapsules标题、正文、开启时间、公开状态
Favoritefavorites用户收藏胶囊的关联表
RefreshTokenrefresh_tokenstoken 哈希、家族 ID、吊销状态

6依赖注入：app/deps.py

FastAPI 的 Depends() 是初学者最陌生的部分：「在执行路由函数前，先帮我准备好某个对象」。本项目三类依赖：get_db() 准备 session；current_user_optional() 有 token 就解析、没有也放行（公开端点）；current_user_required() 必须登录否则 401。

Authorization: Bearer …→ _parse_bearer→ decode_access_token→ payload["sub"] → UUID→ select(User).where(id==…)

7统一响应壳与集中式错误

Envelope 响应壳

class Envelope(BaseModel, Generic[T]):
    success: bool = True
    data: T | None = None
    message: str | None = None
    errorCode: str | None = None

204 No Content 例外——不包 Envelope，main.py 用 middleware 保证 204 没有 body。

错误码 → HTTP 状态

业务统一 raise errors.not_found("…")，不在 service 里构造 HTTPException。映射集中在 ERROR_TO_STATUS：

VALIDATION_ERROR · 422UNAUTHORIZED · 401FORBIDDEN · 403NOT_FOUND · 404CONFLICT · 409RATE_LIMITED · 429

8鉴权与 refresh token 轮转

auth_service.py 负责注册 / 登录 / 刷新 / 登出 / 改密。密码用 bcrypt 哈希，明文不入库。refresh token 的设计是重点：

1
access token 是 JWT，客户端直接携带；refresh token 是随机字符串
2
数据库只存 refresh token 的 SHA-256 哈希，不存原文（库泄露也无法直接当令牌用）
3
每次刷新生成新 refresh token，把旧的标为 revoked
4
若已 revoked 的旧 token 被再次使用 → 认为重放攻击 → 整条 token family 全部吊销

core/security.py 提供底层函数：hash_password / verify_password / create_access_token / decode_access_token / generate_refresh_token / hash_refresh_token。JWT payload 含 sub / nickname / avatarId / iat / exp。

9收藏计数的原子更新

收藏的难点不是插一条 favorites，而是保证 capsules.favorite_count 始终正确。关键是不先读出数字、在 Python 里 +1、再写回，而是让数据库执行原子表达式：

db.execute(
    update(Capsule)
    .where(Capsule.id == capsule.id)
    .values(favorite_count=Capsule.favorite_count + 1)
)
# PostgreSQL 下还会 SELECT ... FOR UPDATE 给胶囊行加锁
if lock and settings.db_driver == "postgres":
    stmt = stmt.with_for_update()

添加收藏流程：查胶囊（不存在/不公开→404）→ 不许收藏自己的 → 已收藏则幂等返回 → 插 Favorite → 原子 +1 → 提交。插入 favorites 与更新计数必须在同一事务。

10双库切换

app/db/engine.py 按 DB_DRIVER 创建 engine。SQLite 有额外设置以适配多线程与并发：

check_same_thread=False
允许多线程使用
foreign_keys=ON
启用外键约束
journal_mode=WAL
提升并发写入
synchronous=NORMAL
安全与性能折中

跨库 UUID / 时间戳由 SQLAlchemy 类型层处理：Uuid（SQLite 存 CHAR(32) hex）+ UTCDateTime TypeDecorator（读时补 UTC tz）。这是后端双库三解法里的「A 类 · 类型层挂适配器」。
