总体介绍

HelloTime Pro 的产品载体是“时间胶囊”：用户写下一段内容，设定未来开启时间，到期前只显示元信息，到期后才能阅读正文。

项目定位

它不是生产运营产品，而是多技术栈对比学习项目。所有实现必须对外行为一致，内部写法则尽量体现各技术栈的惯用模式。

核心学习价值

同一套需求在不同语言、框架、渲染模型和数据访问抽象下会呈现完全不同的工程形态，差异可被逐层对照。

当前状态

M0、M1、M2、M3 已完成。全部 20 个实现已落地，契约验证和 UI 冒烟验证覆盖最新主流程。

总体设计

项目的关键不是“写了很多实现”，而是让这些实现被同一套规范、样式和验证系统约束住。

五条设计原则

  • 规范即单一事实源：API、数据库、设计令牌都从 spec/ 出发。
  • 栈内正交：每个实现采用本技术栈的地道模式。
  • 外部一致：路由、JSON、错误码、页面行为和样式一致。
  • 最小脚手架：run、build、test 是统一入口。
  • 教学可读优先：清晰展示主流程，不追求过度优化。

端口与运行形态

后端在 29000-29090，SPA 前端在 7173-7180，全栈在 7177-7182，代理在 9080，开发管理 UI 在 9090。前端经代理切换后端，全栈实现自包含。

业务与数据模型

业务很小，但覆盖了账号、JWT、公开列表、私密访问、收藏、分页、搜索、跨库时间和 UUID 等典型 Web 应用问题。

用户旅程

  • 匿名用户浏览胶囊广场，按最新/最热排序，按已开启/未开启过滤。
  • 注册用户创建胶囊，选择是否加入广场，并获得 8 位分享码。
  • 任何人可用 8 位码打开胶囊，到期前只看元信息，到期后读正文。
  • 登录用户收藏公开胶囊，在“我的收藏”中回访。

关键不变式

  • 胶囊 content 和 openAt 创建后不可修改。
  • favorite_count 必须等于收藏表实际数量。
  • 不能收藏自己的胶囊，不能收藏私密胶囊。
  • SQLite 时间戳作为文本比较，必须注意 ISO 格式一致性。

鉴权流程

所有实现遵守同一套 JWT access token + 不透明 refresh token 轮转模型。全栈实现额外处理 httpOnly cookie 与 Bearer 的桥接。

Access Token

JWT HS256，有效期 1 小时，payload 包含用户 id、昵称、头像、签发时间和过期时间。适合高频无状态校验。

Refresh Token

256-bit 随机串，客户端持有明文，数据库只存 sha256 hash。有效期 7 天，可吊销，可做家族追踪。

轮转与重放

每次 refresh 撤销旧 token 并签发新 token。若旧 token 被再次使用，整条 family 全部撤销，要求用户重新登录。

验证体系

本项目强调黑盒验证。契约验证不读实现代码，只从 HTTP 行为判断是否符合规范；UI 冒烟从真实浏览器验证主流程。

前后端与全栈对比

对比时要抓住三条主线：后端的抽象厚度，前端的响应式模型，全栈的前后端边界。

后端：抽象厚度

从原生 SQL 到重型 ORM，控制力、样板量、跨库适配成本各不相同。Spring/JPA 最省 CRUD，但跨库要下沉到 Hibernate SPI；Axum/Drogon/Vapor 手写较多，但边界透明。

前端：状态到 DOM

React 重跑组件并 diff，Vue/Angular 自动追踪，Svelte 编译期消除框架，Solid 细粒度直达节点。页面相同，差异都落在响应式心智上。

全栈：边界位置

Next/Nuxt 让前后端边界模糊，浏览器下载并 hydrate 框架；Rails/Spring/Laravel 保持服务端模板主导，只用 Turbo/HTMX/Alpine 做局部增强。

维度左侧策略右侧策略学习观察点
数据访问原生 SQL / 手写编解码ORM / 类型转换器抽象越厚，日常越省，跨库边界越深。
前端渲染编译期或细粒度虚拟 DOM 与变更检测运行时体积、心智模型和显式接线互相交换。
全栈页面服务端模板 + 局部增强同构 SSR + hydration客户端 JS 体量与前后端接缝成本相互权衡。
鉴权Bearer APIhttpOnly cookie SSR全栈实现需要 cookie 到 Bearer 的身份桥。

十个后端实现详解

十个后端均实现同一套 /api/v1/* 契约，均支持 PostgreSQL 与 SQLite，差异主要来自语言、数据访问方式、事务表达和跨库适配。

五个前端实现详解

五个 SPA 前端通过 :9080 代理访问当前选中的后端，路由、页面、交互和视觉一致，主要差异是响应式和状态管理。

五个全栈实现详解

全栈实现是一个进程两张脸：一张 JSON API 给契约测试和浏览器 fetch，一张 SSR HTML 页面给用户导航。

建议学习路线

按“规范 → 参考实现 → 同类对比 → 全栈边界”的顺序读，效率最高。

1. 先读规范

从需求、总体设计、数据库 schema、鉴权流程开始，理解所有实现共同遵守的边界。

2. 读参考栈

FastAPI + React 是 M1 参考实现，适合作为业务流程、API 形状和 UI 状态的基线。

3. 横向对照

后端按数据访问和事务读；前端按响应式模型读；全栈按 HTML 生成位置读。

4. 用验证收束

每看完一个实现，跑契约或 UI 冒烟，确认“内部不同、外部一致”这一核心目标。
